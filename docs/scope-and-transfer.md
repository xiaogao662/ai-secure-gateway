# 模型模式与场景迁移

项目定位：**面向 AI 工具调用的数据访问安全原型，以申请材料作为验证场景。** 重点不是留学业务本身，也不是让模型识别所有攻击话术，而是把不可信的工具提议与后端权限判断分开。

## Mock 是什么，哪些部分是真的

Mock 是固定规则模拟器，不是本地语言模型。当前代码匹配少量列表表达，并用规则从读取请求中提取材料编号；不匹配时不提出工具调用。它没有理解语言的模型，也不把完整的成功或失败回答预先写好。

| 环节 | Mock 模式 | DeepSeek 模式 |
| --- | --- | --- |
| 选择工具 | 本地固定规则 | 外部模型依据当前消息和工具说明提出调用 |
| 登录与权限判断 | 真实后端 | 同一套真实后端 |
| 授权后解密、写审计 | 实际执行 | 实际执行 |
| 对闲聊的处理 | 无匹配规则时返回固定澄清 | 无工具提议时返回固定澄清；不展示模型自写聊天内容 |
| 模型费用 | 无 | 有效请求可能计费，包括无关问题 |
| 能支持的结论 | 网关、加密、日志与界面路径的验证 | 特定真实模型提议经过网关处理的证据 |

模拟测试可以稳定构造未知工具、非法参数、越权目标等情况，帮助检查后端。它不能证明真实模型受到提示注入，也不能提供真实模型的话术成功率。

## 相似话术与同一个工具

例如“读取材料 2”“打开编号 2 的申请材料”“给我看看第二号材料”，预期意图都可能对应：

```json
{"tool_name":"read_application","arguments":{"application_id":2}}
```

这些是解释性例子，不是已经逐条验证的真实模型结果。DeepSeek 可能选择同一个调用，也可能选错工具、参数或不调用；不能保证每次一致。Mock 只按现有规则处理，并不保证支持这些改写。

如果模型错误地请求了用户自己有权访问的另一份材料，网关可能允许：它负责权限，不保证模型选中了用户想要的目标。如果模型请求的是无权访问的材料，网关必须拒绝。也不要让模型仅凭“Bob 的材料”猜测编号；姓名和材料编号不是天然等同的。

这区分了两个问题：**任务正确性**是“做的是不是用户想做的事”；**访问安全性**是“是否做了这个用户无权做的事”。本项目主要验证后者，两者不能混为一谈。

## 申请材料以外能类比什么

下表是设计迁移思路，**不是已实现功能**。真实业务必须重新确认其权限规则。

| 当前场景 | 可类比场景 | 可以复用的检查思路 | 必须重新定义的部分 |
| --- | --- | --- | --- |
| 学生访问自己的材料 | 员工访问自己的报销单 | 根据服务器身份检查资源所有者 | 报销字段、财务角色和审批状态 |
| 导师访问已分配学生的材料 | 客服查看分配给自己的工单 | 根据明确分配关系限制读取 | 工单分配、团队范围和客户信息 |
| 管理员查看访问日志 | 安全人员查看系统审计 | 管理接口独立检查角色、关联请求编号 | 审计范围、保留期限与敏感信息策略 |

例如迁移到报销读取，不只是把页面上的“申请材料”改成“报销单”。需要新的资源表、工具参数、权限查询和测试；财务审核人员也不能直接等同于当前拥有全部读取权限的管理员。

## 哪些可沿用，哪些还没有通用化

可沿用的基础思路：服务器会话、执行前身份复验、工具允许清单、严格参数检查、先授权后解密、日志失败不交付结果，以及限流。

当前仍与申请材料绑定的实现：list_applications/read_application 两个工具、学生与导师权限查询、字段加密的记录绑定信息，以及审计中的 application_id（材料编号）。所以目前不能宣称“任意工具即插即用”。

若以后做第二个示例，可先限定为“只读报销单”，不增加审批、付款等写入操作。验证重点是两类资源权限不串用、资源类型与编号一起参与授权、拒绝时不解密，以及审计能区分资源类型。这是后续设计计划，本轮未实现。

## 展示时怎么说

“我用申请材料建立了一个小型、多角色数据集，重点验证 AI 提出的工具调用不能突破用户已有权限。Mock 用于稳定复现后端测试，DeepSeek 用于观察真实工具提议。该架构思路可以迁移到报销或工单读取，但当前实现和证据仍限定在申请材料场景。”
